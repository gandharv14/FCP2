# Quarantine chain inventory adapter — isolated proposal

This proposal adds `xl_table_quarantine_inventory.py` and one explicit dispatch branch in `xl_source_inventory._validate_transformation`, plus controller and original-source lineage integration. It writes no source approval, registry entry, production inventory, tracker or release. The ordinary source-health and recalculation receipt policies are unchanged.

## Exact route and trust boundary

The new `source-transformation-lineage/v2` record uses policy `quarantined-table-source-inventory/v1`. Record construction requires the caller's independently frozen original SHA, retained curation SHA and complete ordered target identity. It independently validates original → signed, table-complete quarantined intermediate → strictly reconstructed, dependency-excluded, leak-checked materialized candidate. Actual retained staging is mandatory. The final candidate must have current `pass` or `restricted_pass` health and no data tables. All original files remain separate.

Producer identity and public key are never accepted as record, receipt, CLI or caller parameters. The adapter reads the fixed root-protected `/etc/harbor/excel-table-quarantine.json`, `/etc/harbor/excel-runner.json`, and `/Library/Application Support/FCP2/recalc/table_quarantine_runner.py`. It verifies root ownership and protected parents, hashes the actual producer, and compares the protected observer implementation to current observation code. The public key path/hash comes only from the independent protected base config. All six configured controls must be literal true; the signed receipt independently requires the actual six controls. The request engine must be in the protected permitted-version list, which must contain unique concrete numeric dotted versions; blank, wildcard, duplicate and malformed entries reject. Full trust-file hashes and the current adapter bytes are bound into the record and rechecked after proof validation. No private key is read.

Every validation reconstructs the full expected record, including current health, exact file bindings, current producer/policy and original source identity. A historically valid chain, forged pass label, rehashed altered record, ordinary receipt, missing staging, stale verifier, in-cone table or nonunique recurrence cannot establish this route. Previous v1 transformations use their existing validator unchanged.

The existing approved-cohort ledger still records `transformation.original_source`, so each original workbook remains counted once. `source_approval` and `task_approval` in the transformation are always false: the record is evidence, not authority.

## Controller integration included in the isolated patch

1. Build the explicit record with `quarantine_workbook_record(lineage_path=..., original=..., staged=..., intermediate=..., candidate=..., curation=..., request_path=..., result_path=..., materialization_path=..., expected_workbook=..., expected_original_sha256=..., expected_curation_sha256=..., expected_ordered_outputs=...)`. The caller obtains expected identities from frozen source/curation evidence, never the quarantine result.
2. Assemble a new, append-only versioned inventory with the existing `assemble_inventory_manifest`; preserve every original in the denominator and preserve prior inventories/approvals.
3. After independent review and an explicit commit-pinned registry entry, call `resolve_approved_quarantine_record(inventory, workbook_id=..., batch_id=...)`. It accepts no registry override and uses the existing full-cohort approval validator. This gate is mandatory **even when final health is pass**. No matching approval means no adoption.
4. Only then run the normal final candidate source/AST publication and fresh strict segmentation under unchanged retained curation. The quarantine result is not passed off as an ordinary source recalculation receipt. Existing source/segmentation activation, reconstruction, immutable publication/CAS and all Harbor gates remain mandatory.

`scripts/corpus_build.configured_quarantine` selects this route only when the explicitly supplied source inventory contains a v2 record for that original workbook. It rejects any competing ordinary recalculation request/result. Controller admission validates approval, original corpus hash and exact retained curation, then binds the complete adoption checkpoint hash. The worker revalidates and compares that hash before using the final candidate; it preserves original intake classification and evidence. It bypasses only re-running an already completed materialization and still runs the existing final source identity publication, segmentation, current preflight and exact ordered-target comparison.

The normalization checkpoint records inventory artifact path/hash, approved batch and exact approval digest, original/final hashes, complete chain file/hash, curation/ordered targets, transformation digest and protected policy digest. Source-checkpoint dependencies bind this complete object. Both source reuse and VERIFIED reuse independently validate it; missing/revoked approval or stale evidence cannot become a cache hit. `scripts/corpus_lineage.validate_normalization` invokes the same validator when mapping a published final source back to its original, so parent promotion/original-identity checks receive the same chain evidence. No automatic fallback to a legacy transformation or unbound final candidate is supported.

The unpublished chain code-identity contract now binds explicit logical module names and verifier paths relative to the actual publication module repository, plus exact byte hashes. Identical reviewed code copied into a frozen snapshot retains the same semantic identity. Changed code, unexpected/out-of-root verifier paths, duplicate identities and a missing publication implementation reject. Input, artifact, staging, curation, receipt and proof-generation paths remain exact. No historical issued chain is rebound; none existed under the unpublished path-dependent proposal. The signed profile observation receipt remains independently validated against its exact selected code hashes. Final request/config identities must use the latest reviewed source-recalculation module bytes, including the separately tested streaming snapshot change.

## Safe installation sequence for later root review

No installation is executed by this proposal, and the old failed ordinary0117 request must not be retried or relabelled.

1. Review the frozen producer/window/profile/consumer/adapter patch and tests. Record the exact existing protected base-config, ordinary implementation and **existing public-key** hashes without displaying or copying private-key bytes. Retain protected backups of the existing implementation/config. Verify the dedicated console account UID and exact permitted Excel version independently.
2. The installed ordinary implementation must include the reviewed complete-table observation helper. If its current hash differs, install the reviewed compatible ordinary implementation through a root-owned temporary file in the same protected directory; verify hash, mode0755 and root owner, then atomically replace. Update only the protected base config's implementation hash/path as reviewed using the same protected atomic pattern. Preserve `receipt_private_key`, `receipt_public_key`, public-key hash, automation account and isolation settings. Never rotate a key to make historical evidence pass. Run ordinary runner preflight and historical signed-result revalidation before proceeding; infrastructure failures remain blockers.
3. Root-install the reviewed separate producer and window scripts under `/Library/Application Support/FCP2/recalc/`, mode0755 with protected parents. Create the separate root-owned0700 journal tree and root-owned0755 artifact tree with protected invoker-traversable parents. These paths must be new or independently checked; do not remove replay journals or completed evidence.
4. Fill the reviewed table config with the independently verified UID, exact permitted Excel version, existing base config path, installed observer/dispatcher hashes, current selected pipeline policy hashes and protected journal/artifact roots. Install it atomically root-owned0644 (or another reviewed invoker-readable, non-writable mode) at the fixed table-config path. Verify `protected_policy()` as the ordinary pipeline user; any ownership/hash/current-code discrepancy fails closed.
5. After parent approval of all integration, prepare a **fresh new-domain request UUID** with the current original0117 hash and protected artifact destination. Use the persistent `.venv/bin/python`3.12 precheck, then the separately protected system-Python window. The window serializes with ordinary Excel, disables/restores networking, retains staging/results/full private diagnostics, and prints only concise status/paths/hashes. No ready-to-run Terminal command or request is issued here.
6. Validate the complete receipt/derived semantics and both chain edges, explicitly approve the new inventory, and run every final source/segmentation/Harbor gate. A trusted recalculation can still fail semantic checks or reconstruction; it is not a promised0117 recovery.
